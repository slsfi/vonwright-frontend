# v4 breaking changes and fork migration notes

> [!NOTE]
> These notes describe the breaking changes introduced in **v4.x.x** of the base app and assume the fork is on the **latest v3 release**. Earlier breaking changes are documented in the [v2](v2.md) and [v3](v3.md) notes.

v4 has not yet been tagged. Use the final release notes and tagged source when upgrading a production fork.

## 1. Relocate configuration, styles, and public files

v4 changes several file locations, grouping project configuration and style overrides under `src/project/` and static assets, crawler documents, and generated HTML under `public/`.

Apply this mapping to the edition's own files, including extra assets that are absent from the base app:

| v3 location | v4 location |
| --- | --- |
| `src/assets/config/config.ts` | `src/project/config.ts` |
| `src/assets/custom_css/custom.scss` | `src/project/global-overrides.scss` |
| `src/global.scss` | `src/styles.scss` |
| `src/assets/fonts/` | `public/assets/fonts/` |
| `src/assets/images/` | `public/assets/images/` |
| `src/assets/ebooks/` | `public/assets/ebooks/` |
| `src/assets/files/` | `public/assets/files/` |
| `src/assets/icon/favicon.ico` | `public/favicon.ico` |
| `src/robots.txt` | `public/robots.txt` |
| `src/sitemap.txt` | `public/sitemap.txt` |
| `src/static-html/` | `public/static-html/` |

Carry the edition's configuration and style overrides into the new files. Update any direct imports, file replacements, or custom scripts using the old paths. Move ignored local configuration variants separately to `src/project/config-*.ts`; Git does not move ignored files during a merge.

Keep the fork's commented-out stylesheet inclusions when renaming `global.scss`. The global `styles` array in `angular.json` must retain this order:

```json
"styles": [
  "src/styles.scss",
  "src/project/global-overrides.scss"
]
```

If the fork has custom Sass font references, update their relative paths to `public/assets/fonts/`. From `src/theme/font-face/`, the path is `../../../public/assets/fonts/...`.

In `angular.json`, the `build.options.assets` list tells Angular which files to copy into the browser output. Adopt the upstream entries that copy `public/`, removing the old entries for `src/assets/`. If the fork added its own entries, update their `input` paths to match the moved files.

The sitemap and static-menu generators now write to `public/sitemap.txt` and `public/static-html/collection-toc/`. Regenerate enabled output in those locations before building, and update any custom scripts that use the old output paths.

## 2. Merge the integrated build and locale configuration

Adopt the new upstream targets in [`angular.json`](../../angular.json) while preserving the edition's locale configuration:

| Target | v4 builder |
| --- | --- |
| `build` | `@angular/build:application` |
| `serve` | `@angular/build:dev-server` |
| `test` | `@angular/build:unit-test` |
| `extract-i18n` | `ng-extract-i18n-merge:ng-extract-i18n-merge`, delegating to `@angular/build:extract-i18n` |

The application target replaces separate browser/server builds. Remove the old `server`, `serve-ssr`, and `prerender` targets and unsupported options such as `buildOptimizer`, `vendorChunk`, and locale-specific `deleteOutputPath` overrides. Retain any edition-specific file replacements and supported build options when merging.

### Preserve the edition's languages and URL prefixes

Retain the edition's `i18n` settings, translation files, locale-specific configurations, and production `localize` list rather than adopting the base app's language list.

Convert each locale's old `baseHref` setting to `subPath` without the surrounding slashes: `"baseHref": "/sv/"` becomes `"subPath": "sv"`. For example:

```json
"sv": {
  "subPath": "sv",
  "translation": "src/locale/messages.sv.xlf"
}
```

Use the locale code as `subPath`, matching the app's language links and generated URLs. Retain a deployment-wide `build.options.baseHref` if the site runs under a directory prefix. Check that the emitted locales match `app.i18n.languages` and `defaultLanguage`, and that nginx's `$default_locale` points to the default language's emitted subpath.

### TypeScript and localization setup

`tsconfig.server.json` is removed; browser and server sources share `tsconfig.app.json`. If the fork added compiler options to the old server configuration, transfer the necessary settings to the application configuration.

Set `extract-i18n.options.builderI18n` to `@angular/build:extract-i18n` and preserve the edition's `targetFiles`. Review the translation diff after running extraction.

### Page-not-found message

The page-not-found page now uses localized interface text instead of fetching backend Markdown with the node ID `{language}-404` (for example, `sv-404`). Changes to those backend documents no longer affect the page.

If the edition has a custom 404 message, move its wording into the `PageNotFound.DefaultMessage` translation target in each `src/locale/messages.<locale>.xlf` file. The heading uses `PageNotFound.404PageNotFound`, and the home-page link text uses `PageNotFound.GoToHome`; preserve the link placeholder when translating. See [interface translation guidance](../PROJECT-CUSTOMIZATION.md#translate-interface-messages).

### Content-page introduction

The content page now uses the `Content.Introduction` interface translation for the introduction above its grid instead of fetching backend Markdown with the node ID `{language}-02` (for example, `sv-02`). The source and default translation targets are empty, so the base app displays no introduction block or extra spacing.

If the edition uses this backend content, move it into the `Content.Introduction` target in each `src/locale/messages.<locale>.xlf` file. Convert Markdown to HTML and escape it as XML text in the target. Paragraphs, links, and other formatting are supplied entirely by the target, without editing the component's TypeScript or template. The introduction renders through Angular's `[innerHTML]` binding, which sanitizes the HTML. Empty or whitespace-only targets omit the block and its spacing. Collection and cover data used by the content grid continue to load as before.

#### Example: two paragraphs in English

For a fork configured to emit the `en` locale, run `npm run extract-i18n`, then replace only the `<target>` inside the `Content.Introduction` unit in [`src/locale/messages.en.xlf`](../../src/locale/messages.en.xlf) with:

```xml
<target>&lt;p&gt;Welcome to the edition!&lt;/p&gt;
&lt;p&gt;Browse or &lt;a href=&quot;search&quot;&gt;search&lt;/a&gt; the content.&lt;/p&gt;</target>
```

Keep the generated `<source/>` unchanged. Leave the corresponding `<target/>` empty in any locales where no introduction is wanted, then rebuild and check `/en/content`. The relative `href="search"` keeps the link under the locale's base URL, normally `/en/search`.

## 3. Review proxy trust and custom SSR code

### Proxy trust

Proxy trust now requires both `app.ssr.trustProxyHops` and the new `app.ssr.trustedProxyAddresses` in `src/project/config.ts`. The defaults are two hops and `["loopback", "linklocal", "uniquelocal"]`. Review these against the edition's actual proxy chain; add proxy IPs/CIDRs if they fall outside the default ranges. An empty address list or zero hops disables proxy trust.

For HAProxy -> nginx -> Node, two hops remains appropriate, but the proxy addresses must also be trusted. Forwarded origin headers from an untrusted immediate peer are discarded. See [SSR and proxy settings](../PROJECT-CUSTOMIZATION.md#ssr-and-proxy-settings) for configuration details.

### Only if the fork has custom application code

Reapply custom server changes to [`src/server.ts`](../../src/server.ts): the root entry is removed, `CommonEngine` is replaced by `AngularNodeAppEngine`, and the server build is ESM. Replace server-side `require`/`__dirname` usage with ESM-compatible code.

Services using the old Express `REQUEST`/`RESPONSE` tokens must migrate to optional [`APPLICATION_REQUEST_CONTEXT`](../../src/app/tokens/request-context.token.ts) injection for request information and Angular's nullable `RESPONSE_INIT` for HTTP status changes. Keep browser fallbacks when the request context is absent.

If the fork changed routes or server providers, merge the new generated server-route registration in `app.config.server.ts` and regenerate routes. The old `auth-protected-route-paths.generated.ts` is removed; update any scripts consuming it. See [application architecture](../DEVELOPMENT.md#application-architecture) and [route generation](../DEVELOPMENT.md#feature-based-route-generation) for implementation details.

## 5. Convert fork-owned tests to Vitest

Adopt the Vitest/jsdom test target and `tsconfig.spec.json`. Remove Karma target options, `karma.conf.js`, and the manual `src/test.ts` bootstrap; include the new `src/test-setup.ts`.

Replace fork CI commands using `--browsers=ChromeHeadless`, Karma configuration, or `ng test --configuration=ci` with `npm run test:ci`.

If the fork has additional or modified specs, convert their Jasmine APIs:

| Jasmine API | Vitest equivalent |
| --- | --- |
| `jasmine.createSpy()` | `vi.fn()` |
| `spyOn(object, 'method')` | `vi.spyOn(object, 'method')` |
| `.and.returnValue(value)` | `.mockReturnValue(value)` |
| `.and.callFake(fn)` | `.mockImplementation(fn)` |
| `.calls.count()` / `.calls.allArgs()` | `.mock.calls.length` / `.mock.calls` |
| `toHaveBeenCalledOnceWith(...)` | `toHaveBeenCalledTimes(1)` plus `toHaveBeenCalledWith(...)` |
| `jasmine.clock().install()` / `.uninstall()` | `vi.useFakeTimers()` / `vi.useRealTimers()` |

Replace Jasmine-specific matchers, timer behavior, and spy types. `vi.spyOn()` calls the original method by default, so add a mock implementation where the old Jasmine spy stubbed it. See [development testing](../DEVELOPMENT.md#testing) and the converted upstream specs for examples.

## 6. Merge dependencies, runtime commands, and deployment changes

Merge the upstream `package.json` and `package-lock.json` changes together, including:

- Replace `@angular-devkit/build-angular` with `@angular/build`.
- Add `vitest` and `jsdom`.
- Remove direct Jasmine/Karma dependencies: `@types/jasmine`, `jasmine-core`, `karma`, `karma-chrome-launcher`, `karma-coverage`, `karma-jasmine`, and `karma-jasmine-html-reporter`.

| v3 command or file | v4 replacement |
| --- | --- |
| Separate browser build followed by `ng run app:server:production` | `npm run build:ssr` |
| `node dist/app/proxy-server.js` | `npm run serve:ssr`, running `dist/app/server/server.mjs` |
| `dist/app/browser/<locale subPath>/index.html` | `dist/app/browser/<locale subPath>/index.csr.html` |
| `postbuild-copy-files.js` | Removed. Move any extra fork copy operations to the `assets` list in `angular.json` or a fork script. |

Update any fork launchers, Docker commands, or CI paths that reference the removed entries.

The development server now runs SSR and requires generated route metadata. Each fork-owned `start` or `start:<locale>` script needs a matching `prestart` or `prestart:<locale>` hook running `npm run generate-routes`; see [start-script guidance](../PROJECT-CUSTOMIZATION.md#package-identity-and-start-scripts). Generate routes beforehand when calling `ng serve` directly. If the fork has custom application code that assumes it runs only in the browser, check it with development SSR.

## 7. Verify the edition before deploying

Check the dependency, test-runner, and extraction changes:

```bash
npm ci
npm run test:ci
npm run extract-i18n
```

Review the translation diff. Before building locally, regenerate the edition's enabled sitemap and static menus in their new locations using the [public-content generation commands](../PROJECT-CUSTOMIZATION.md#generated-public-content).

```bash
npm run build:ssr
npm run test:build-output
npm run serve:ssr
```

Verify the migration's effects on the edition:

- Moved assets, fonts, favicon, and generated menus load; `/robots.txt` and `/sitemap.txt` are served at the website root.
- Each production locale keeps its intended URL prefix, and unprefixed requests use the edition's default language.
- An unknown URL displays the intended localized 404 message, links to the same locale's home page, and returns HTTP 404.
- Each locale's content page displays the grid and any translated introduction; an empty introduction adds no block or spacing.
- Public pages render through SSR; if auth is enabled, protected pages and login/session flows work.
- Canonical/Open Graph URLs retain the public HTTPS origin through the deployment's proxy chain.
- The edition's locale-specific development start commands work with SSR.

Use [edition-specific SSR smoke checks](../DEVELOPMENT.md#ssr-smoke-test-local-or-remote) where available, and follow [deployment](../DEPLOYMENT.md#deployment) for rollout. Record the checks in the upgrade PR.
